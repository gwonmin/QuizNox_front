## Prompt Engineering vs Context Engineering

Zero-shot, Few-shot, Chain-of-Thought 같은 지시문 작성 기법은 <DocLink slug="llm-basics">LLM 기초</DocLink>의 Prompt Engineering에서 다뤘다. 여기서는 그 지시문을 포함해 모델이 보는 입력 전체를 다룬다.

<KeyTable
  columns={["구분", "Prompt Engineering", "Context Engineering"]}
  rows={[
    ["대상", "지시문(system prompt, 사용자 프롬프트)의 문장", "지시문 + 도구 정의 + 검색 결과 + 기억 + 상태 + 대화 + 도구 결과 전체"],
    ["시점", "작성할 때 한 번", "모델을 부를 때마다 매번 (Agent는 한 작업에 수십 번)"],
    ["주요 질문", "어떻게 말해야 모델이 잘 따르나?", "이번 호출에 무엇을 넣고 무엇을 빼야 하나?"],
    ["실패 양상", "지시를 오해함", "필요한 정보가 없거나, 너무 많아서 중요한 정보를 놓침"],
  ]}
/>

> Anthropic은 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)에서 Context Engineering을 Prompt Engineering의 자연스러운 다음 단계로 보고, 모델의 주의(attention)가 한정된 자원이므로 "원하는 결과의 가능성을 최대화하는 가장 작은 고신호 토큰 집합"을 찾는 것이 목표라고 정리한다.

<DocLink slug="rag">RAG</DocLink>는 이 중 "검색 결과"를 채우는 기법 하나이고, Context Engineering은 그 결과를 다른 정보와 함께 어떻게 배치할지까지 포함하는 더 넓은 개념이다.

## 핵심 기법

<KeyTable
  columns={["기법", "방법", "예시"]}
  rows={[
    ["고르기 (Just-in-time)", "모든 데이터를 미리 넣지 않고, 파일 경로·쿼리·링크 같은 참조만 두고 도구로 필요할 때 읽게 한다.", "코드 Agent가 전체 저장소 대신 파일 목록을 보고 필요한 파일만 연다."],
    ["줄이기 (Compaction)", "컨텍스트가 한도에 가까워지면 지금까지의 내용을 요약해 새 컨텍스트로 이어간다. 도구 원본 결과는 핵심만 남긴다.", "긴 디버깅 세션에서 '시도한 것·결과·남은 가설'만 남기고 로그 원문은 버린다."],
    ["나누기 (Isolation)", "깊은 탐색은 하위 Agent에게 맡기고, 메인 Agent에는 짧은 요약만 돌려받는다.", "조사용 하위 Agent가 문서 20개를 읽고 결론 한 단락만 반환한다."],
    ["밖에 남기기 (Notes)", "진행 상황·결정·할 일을 컨텍스트 밖(파일, DB)에 적어 두고 필요할 때 다시 읽는다.", "작업 계획 파일을 두고 단계가 끝날 때마다 갱신한다. State & Memory 문서 참고."],
    ["순서 정하기", "자주 바뀌지 않는 부분(지시문, 도구 정의)을 앞에, 자주 바뀌는 부분을 뒤에 둔다.", "앞부분이 매번 같으면 프롬프트 캐시가 적중해 비용과 지연이 줄어든다."],
  ]}
/>

<Callout variant="info" title="프롬프트 캐시와 순서">
  <p>주요 모델 API는 입력의 앞부분이 이전 요청과 같으면 그 부분을 캐시해 더 싸고 빠르게 처리한다. 매 호출마다 맨 앞에 현재 시각이나 요청 ID처럼 바뀌는 값을 넣으면 캐시가 깨진다. 캐시의 일반 원리는 <DocLink slug="caching">Caching</DocLink> 문서와 같다.</p>
</Callout>
