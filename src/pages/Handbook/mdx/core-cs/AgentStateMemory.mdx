## State와 Memory의 차이

<KeyTable
  columns={["구분", "State (작업 상태)", "Memory (기억)"]}
  rows={[
    ["수명", "한 작업(run)이 끝날 때까지", "세션 · 사용자 단위로 계속"],
    ["예시", "계획, 완료한 단계, 다음 단계, 도구 호출 결과 요약", "사용자 선호, 확인된 사실, 지난번에 실패한 방법"],
    ["주 용도", "중단 후 재개, 다음 단계 결정", "개인화, 같은 실수 반복 방지"],
    ["잘못되면", "작업이 꼬이거나 처음부터 다시 함", "틀린 정보가 계속 사실처럼 쓰임"],
  ]}
/>

이 구분은 <DocLink slug="stateless-stateful">Stateless vs Stateful</DocLink>과 같은 원리다. Agent 서버 프로세스는 stateless로 두고, 상태와 기억은 외부 저장소에 둬야 서버를 늘리거나 재시작해도 작업을 이어갈 수 있다.

## 저장소 선택

<KeyTable
  columns={["저장소", "적합한 기억", "이유"]}
  rows={[
    ["KV (Redis, DynamoDB 등)", "작업 상태 · checkpoint · 세션", "키로 바로 읽고 쓰며 빠르다. TTL로 자동 만료시키기 쉽다."],
    ["RDB", "프로필 · 선호 · 확인된 사실 · 기억 변경 이력", "구조가 정해져 있고, 수정·삭제·감사가 쉽다. 사용자가 자기 기억을 보고 지울 수 있게 만들기 좋다."],
    ["벡터 저장소", "경험 기억 · 비정형 메모", "정확한 키 없이 '비슷한 상황'을 찾아야 할 때 쓴다. Vector DB 문서 참고."],
  ]}
/>

벡터 검색은 강력하지만 "비슷하지만 틀린" 기억도 찾아온다. 사용자 이름이나 설정처럼 정확히 맞아야 하는 정보는 <DocLink slug="vector-db">Vector DB</DocLink>보다 RDB에 키로 저장하는 편이 안전하다.

## 무엇을 기억하지 않을 것인가

<Callout variant="warning" title="기억은 쓰기 정책이 먼저">
  <p>Agent가 본 것을 전부 저장하면 기억이 금방 오염된다. 저장하기 전에 "이 정보가 다음에도 사실이고, 쓸모 있고, 저장해도 되는가"를 통과해야 한다.</p>
</Callout>
